# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

> Note: this CLAUDE.md is for developers maintaining Grimoire. It is **not** loaded for end users — the installer clones the repository into the Grimoire home but copies only `skills/grimoire-*` into the agents' skill directories. End-user context comes from the skills and from [GRIMOIRE-CONVENTIONS.md](GRIMOIRE-CONVENTIONS.md).

## What this repo is

Grimoire is a set of **thirteen skills** for Claude Code and Codex that define the Grimoire workflow — Spec → Plan → Execute with an autonomous review loop ending in a pull request, `grimoire-run` for whole constructs, a Quick fast-path, and orthogonal context / Q&A / dependency / maintenance skills — plus the **installer** that distributes them.

- **Skills.** One `skills/<name>/SKILL.md` per skill: YAML frontmatter (`name`, `description`, `argument-hint`) and a prompt body that opens with a `[Required Reading]` block and continues in numbered phases.
- **Single source of truth.** Every shared, load-bearing rule lives in [GRIMOIRE-CONVENTIONS.md](GRIMOIRE-CONVENTIONS.md), organised in `§` sections. Skill bodies reference it as `${GRIMOIRE_HOME}/GRIMOIRE-CONVENTIONS.md` and name the sections they depend on; they never restate a rule.
- **Installer.** `install.sh` (POSIX sh: clone/update the home, copy the skills, substitute `${GRIMOIRE_HOME}`, install `deps.txt`, create the global config), `install.ps1` (Windows wrapper running `install.sh` through Git Bash), `deps.txt`, `config.example.toml`, `VERSION`, and the VERSION-driven `.github/workflows/release.yml`. There is no plugin manifest.
- **No build, no source code.** The only test suite is `bash scripts/test-install.sh` (sandboxed `HOME`, offline); the lint is `sh -n install.sh`. Edits land in the markdown of the files above.
- **Neutral docs** for humans live in [docs/](docs/); this repository's own Grimoire index is [.grimoire/PROJECT.md](.grimoire/PROJECT.md).

## Vocabulary

- **Page** — the unit of work: one feature, fix, or alteration. GitHub backend: an issue whose body is the SPEC (marker `<!-- grimoire:page v=1 … -->`), its plan a comment, its work one PR. Local backend: `.grimoire/pages/NNN-<slug>/` (`SPEC.md`, `PLAN.md`, `K-<step>.md`, `REVIEW.md`, `NOTES.md`), git-ignored. Status: `reference` → `spec` → `planned` → `review`, plus `blocked`; `done` locally. Use "page" — not "feature", "ticket", or "task" — in skill bodies and docs.
- **Construct** — a larger-than-a-page objective: a flat, ordered list of references. GitHub: a milestone (`<!-- grimoire:construct v=1 -->` + a numbered `## References` list). Local: `.grimoire/constructs/NNN-<name>/` (`CONSTRUCT.md` + `references/N-<short-name>.md`), git-ignored. A construct carries no status, branch, or PR of its own — only its pages do.
- **Reference** — one page-sized seed of a construct. On GitHub it is an issue labelled `grimoire:reference`, created immediately, whose number becomes the page number when `grimoire-spec` consumes it; locally a file with `status: pending | specced`. Specced references form an immutable locked prefix.
- **Backend** — where workflow state lives: **GitHub** (issues, milestones, comments, PRs, labels `grimoire:*`) or **local** (git-ignored files). Detected once per run from `[github].mode`, the `origin` host, and `gh auth status`, and announced (`🔗` / `📁`). No backend ever produces a state commit.
- **Run** — one `grimoire-run` invocation over a construct: interactive spec interviews, the `🚀` boundary, then autonomous page waves, tracked in a ledger `.grimoire/bag/runs/<construct>-<epoch>.md`.
- **Role** — the configuration identity of a sub-agent (`research`, `plan`, `execute`, `fix`, `review`, `quick`, `deps`, plus the notice-only `session` and the `default` fallback), resolved to a model + effort per harness from `config.toml`.
- **Page worktree** — `.grimoire/bag/worktrees/page-<N>/` on the branch `grimoire/<N>-<slug>`, where a page is executed and reviewed so the user's working tree never changes branch; parallel steps use nested `page-<N>-step-<K>/` worktrees. Always torn down at the end of a run; the branch remains.
- **Harness** — Claude Code or Codex, detected from the tools present (`Agent` vs `spawn_agent`).

## The skills and how they connect

- **`grimoire-init`** — Analyzes the consuming project (README, manifests, build/CI config, layout), discovers the `[verify]` commands without running them (`{port}` when the dev tool accepts a port flag), and interviews the user about what cannot be inferred. After one draft review it writes the neutral `docs/` files (only the missing canonical ones — never rewriting human docs), the `.grimoire/PROJECT.md` index with `## Grimoire rules`, `.grimoire/config.toml` (`[verify]`, `[docs]`), and the `# Grimoire` `.gitignore` block; on GitHub it ensures the labels. Update mode asks only about deltas and never overwrites existing config values. Detects 0.13 state tracked by git and migrates it on explicit consent (stamp frontmatter, untrack, delete `HISTORIC.md` / `bag/historic/`, `chore(grimoire): migrate to 0.14 layout`). Spawns nothing. Commits `docs(grimoire): initialize project context` / `update project context`.
- **`grimoire-spec`** — Entry point of the pipeline and the only skill that opens a page from free text. A `research` sub-agent analyzes the code; size evaluation may recommend a construct (handoff brief `.grimoire/bag/drafts/construct-brief-<epoch>.md`, then STOP without a page); the interview runs to consensus; after draft review the SPEC becomes an issue labelled `grimoire:spec` (GitHub) or `SPEC.md` with `status: spec` (local). A bare number switches to construct-consumption mode: strictly the first pending reference seeds the full interview, the reference issue is rewritten into the page (`grimoire:reference` → `grimoire:spec`), or locally the reference flips to `specced` (and `CONSTRUCT.md` to `status: done` when it was the last). Commits nothing.
- **`grimoire-plan`** — Optional interactive planner; the session plans itself (no `plan` sub-agent). Hard-stops on a missing / unmanaged / unspecified / executing / in-review / finished page. Asks about ambiguities, decides the step breakdown, emits `depends-on` / `touches` only for genuinely independent steps and shows the DAG and waves at the final clarity check, records `## Assumptions`, and after draft review posts the plan comment and swaps the label to `grimoire:planned` (GitHub, plus the local step-file cache) or writes `PLAN.md` + step files and `status: planned` (local). Re-planning is allowed while no page branch exists. Commits nothing.
- **`grimoire-execute`** — Pure orchestrator, asks no questions. Hard-stops per `§ Review loop` (including dependency pages never executed or blocked). Auto-plans a `spec` page through a `plan` sub-agent without interview; creates the page branch from its base (default branch, or stacked on a non-merged dependency) and the page worktree; runs one `execute` sub-agent per step (strict serial, or waves per `§ Parallel execution`); after the first step commit pushes and opens a draft PR; then review rounds up to `[review].max_rounds` — a `review` sub-agent (scope, `ponytail-review`, full test/build/lint gate, UI with `agent-browser` / `impeccable` / `revenue-centric-design`) and a `fix` sub-agent on `changes-requested`. Ends `review` (`gh pr ready`, `grimoire:review`) or `blocked` (draft PR, `⛔` comment with the way back). An existing branch means resume mode. Unconditional worktree teardown; never deletes a branch or closes a PR. Locally: branch + `REVIEW.md`, no PR.
- **`grimoire-run`** — Executes a whole construct per `§ Run`. Phase 1 invokes `grimoire-spec` in consumption mode for every pending reference ("skip the rest" allowed); the `🚀 Autonomous phase …` boundary; Phase 2 builds the page DAG (`depends-on`, else an implicit chain), runs Kahn waves with up to `[run].page_parallelism` pages concurrently, each through the `grimoire-execute` protocol with stacked PRs, flat orchestration, a ledger, a best-effort watchdog with one retry, blocked-propagation to dependents, and a UI-review mutex without `{port}`. Resumes an unfinished ledger without re-interviewing; the `executing` resume case is the only branch deletion in the design. Commits nothing of its own.
- **`grimoire-construct`** — Authors a construct from an objective or a handoff brief: `research` sub-agents decompose it into ordered page-sized references with `depends-on`, the user confirms in an interview, and after draft review it creates the milestone and one `grimoire:reference` issue per reference (GitHub) or `CONSTRUCT.md` + `references/` (local). Deletes the brief on success. Never creates a page; commits nothing.
- **`grimoire-construct-update`** — Alters an existing construct in place (add / remove / reorder pending references, edit a pending seed, rewrite the intro, rename). Hard-stops when the construct does not exist; refuses any change to the locked specced prefix, naming the reference and its page. GitHub: removal = remove from milestone + `grimoire:dropped` + close, no renumbering (only `order=` fields); local: contiguous renumbering of the pending tail, backup until approval, rename by `mv` preserving `NNN`. Commits nothing.
- **`grimoire-adopt`** — GitHub only. Brings an existing issue (→ page, `grimoire:spec`) or milestone (→ construct, issues → `grimoire:reference`, gaps created as new issues) under Grimoire: `research` sub-agent, interview, draft review, then rewrites bodies with the markers while preserving the original text in `<details>` blocks; never closes a human's issue. Hard-stops on the local backend, missing, closed, or already-managed objects. A too-large issue gets the construct handoff brief. Commits nothing.
- **`grimoire-quick`** — Fast-path with a scope gatekeeper (too large → STOP and point at `/grimoire-spec`), a final clarity check, and an inline plan the user must authorize; then one `quick` sub-agent fixes it with TDD and atomic commits on the current branch. No page, no worktree, no PR, no backend detection.
- **`grimoire-know`** — Read-only Q&A through one `research` sub-agent (web search / fetch when needed); answer first, an "uncertain about" list, and `References` only when the web was used. Never writes, commits, or touches `.grimoire/`, `docs/`, or backend objects. Detects the backend only when the question is about pages, constructs, or PRs.
- **`grimoire-note`** — Folds a free-text note into the project context: splits it into rules and routes each to `docs/conventions.md` (how code is written) or `PROJECT.md` `## Grimoire rules` (how the agents behave), with semantic dedup, minimum-word synthesis, and a retroactive consolidation pass every run. Hard-stops when `PROJECT.md` is missing; may create `docs/conventions.md` only. Spawns nothing. Commits `docs(grimoire): refine project context`.
- **`grimoire-deps`** — Dependency auditor: a `research` sub-agent scores security, semver risk, maturity (younger than 14 days → "let it mature"), and reputation; a ranked report the user selects from; a `deps` sub-agent applies each bump alone, gated by the full `[verify]` test/build/lint (documented `§ TDD` exception; `docs/development.md` fallback), one `chore(deps): bump <pkg> to <ver>` commit each, reverting only a failing bump. Breaking upgrades become an upgrade brief for `/grimoire-spec`. Never creates a page or writes `docs/` / `PROJECT.md` / `config.toml`.
- **`grimoire-update`** — Maintains the installation: reads `${GRIMOIRE_HOME}/VERSION`, fetches `main/VERSION` and `CHANGELOG.md`, shows the delta, and on an explicit yes runs `sh "${GRIMOIRE_HOME}/install.sh" --ref v<latest>` (managed clone only; a dev checkout gets `git pull` + `./install.sh` advice, a non-git home the reinstall one-liner). Same flow on both harnesses. Spawns nothing, commits nothing, reads no project context.

## Shared conventions

Every `§` section of [GRIMOIRE-CONVENTIONS.md](GRIMOIRE-CONVENTIONS.md), in file order:

- **§ TDD** — Red/Green/Refactor with filtered test runs; the review gate (full suite) is the documented exception, like `grimoire-deps`.
- **§ Code comments** — comment the unusual, not the routine; applies to `grimoire-execute` and `grimoire-quick`.
- **§ Harness adaptation** — the single mapping of every operation (spawn, wait, ask, invoke a skill, fetch a URL, models) to Claude Code and Codex; install location and the `${GRIMOIRE_HOME}` token.
- **§ Sub-agent spawning** — the orchestrator never implements; the seven roles, who spawns them, serial vs. wave spawning, flat orchestration.
- **§ Configuration** — global and project `config.toml`, key-by-key precedence, role lookup order, the full schema (`[agents.*]`, `[run]`, `[review]`, `[github]`, `[verify]`, `[docs]`), `{port}`.
- **§ Skill composition** — discovery of helper skills, automatic read-only use with the `🧩` announcement, gated write helpers, guardrails, Grimoire-on-Grimoire.
- **§ Parallel execution** — step frontmatter, DAG and cycle detection, Kahn waves, step worktrees with mandatory teardown, failure semantics, serial fallback.
- **§ Commits** — Conventional Commits in English; code commits only (plus the `grimoire-init` / `grimoire-note` docs commits); no state commits; branch and PR rules.
- **§ Backends** — detection and announcement, identifiers, page slug, the GitHub state model (markers, labels, plan / verdict comments, PR body, base and stacking, `gh` cheat sheet, adoption, local cache).
- **§ .grimoire/ layout** — only `PROJECT.md` and `config.toml` are committed; page / construct folders, `bag/` (drafts, runs, reviews, worktrees); local status frontmatter; legacy 0.13 pages.
- **§ Documentation** — neutral `docs/`, the `PROJECT.md` index format, `grimoire-init` duties, the 0.13 migration, `grimoire-note` routing, the dual-writer contract, the `[Required Reading]` order.
- **§ Construct** — storage per backend, reference status, `depends-on` between references, writer contract, consumption, alteration rules, the handoff brief.
- **§ Review loop** — page worktree, hard-stops, resume mode, phases, the reviewer and its verdict, fixer, rounds, outcome.
- **§ Run** — `grimoire-run`: hard-stops, Phase 1, the boundary, Phase 2, ledger, resume, watchdog, stop.
- **§ IDE-aware review** — drafts written to disk for the IDE, throwaway vs. final-destination drafts, backups of git-ignored files, inline fallback.
- **§ User-facing language** — English source strings, runtime rendering in the user's language, verbatim tokens and glyphs.
- **§ Pause-point pattern** — every pause and hard-stop per skill, with the literal `❌` messages.

**Do not duplicate these rules in SKILL.md bodies.** When a rule changes, update `GRIMOIRE-CONVENTIONS.md` only.

## Editing notes

- **Frontmatter** is consumed by Claude Code and Codex: keep the `---` delimiters and the keys `name`, `description`, `argument-hint`; `name` must equal the skill's folder name; `description` must stay ≤ 1024 characters.
- **`$ARGUMENTS` and `$1`** in the bodies are invocation substitutions — preserve them verbatim.
- **`${GRIMOIRE_HOME}`** is a literal token that `install.sh` replaces in every installed `*.md` with the absolute path of the Grimoire home (`cygpath -m` form on Windows). Use it for every reference to a shipped file (`${GRIMOIRE_HOME}/GRIMOIRE-CONVENTIONS.md`, `${GRIMOIRE_HOME}/VERSION`, …) — never hardcode a path.
- **Sections.** When you add or remove a `§` section in `GRIMOIRE-CONVENTIONS.md`, update the `[Required Reading]` block of every SKILL.md that depends on it.
- **`VERSION`** (one line) is the release source of truth. A release is one commit that bumps it and adds the `## [X.Y.Z] — YYYY-MM-DD` entry to `CHANGELOG.md` (plus its link reference); `release.yml` tags `vX.Y.Z` and publishes the release from that entry when `VERSION` changes on `main`.
- **`deps.txt`** — one dependency per line, whitespace-separated `type source name [post-step]`; `#` comments and blank lines ignored. `skill` → `npx -y skills add <source> --skill <name> -g -y -a <claude-code|codex>` (`--copy` on Windows); `npm` → `npm install -g <source>` unless `<name>` is on the `PATH`, then the post-step. Dependencies are installed from upstream, never vendored; a failure is a warning.
- **Installer changes** — keep `install.sh` POSIX sh (no `sed -i`, quote every path) and run `bash scripts/test-install.sh` before committing.
- **`.superpowers/`** is git-ignored scratch — never commit it.
- **This repo's own `.grimoire/`** holds only `PROJECT.md` and `config.toml` (committed); everything else under it is git-ignored, as in any consuming project.
- **After editing skills or conventions**, run `./install.sh` from the checkout (dev mode) to refresh the installed copies under `~/.claude/skills/` and `~/.agents/skills/` — the agents read the copies, not the checkout.
